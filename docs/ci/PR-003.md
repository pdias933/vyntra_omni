# PR 003 — integração contínua e guardas

## Objetivo

Bloquear uma alteração quando falhar lint, tipos, testes, build, auditoria de dependências ou detecção de segredos, sem conceder ao código do pull request acesso de escrita, segredo ou ambiente de deploy.

## Escopo incluído

- workflow para `pull_request`, alterações da `main`, execução manual e agenda semanal;
- Node.js e pnpm nas versões exatas do repositório;
- instalação somente pelo lockfile congelado;
- lint, typecheck, testes e build de API, web, iOS e Android;
- auditoria da árvore completa, inclusive ferramentas de desenvolvimento executadas pela CI;
- exceção estreita, verificável e temporária para `GHSA-w5hq-g745-h8pq`;
- Gitleaks sobre todo o histórico Git, com binário, checksum, configuração e canário fixados;
- testes que validam a política do próprio workflow;
- `CODEOWNERS` para workflow e guardas de dependência.

## Fora do escopo

- deploy, publicação de imagem ou artefato;
- staging, produção, migration, banco, Redis ou storage;
- cobertura mínima de testes enquanto ainda não existe domínio implementado;
- geração ou uso de segredo;
- cache compartilhado entre execuções;
- aprovação automática de pull request;
- correção forçada de dependência fora da matriz suportada pelo Expo.

## Portões

### Qualidade e build

Executa, em runner GitHub-hosted Ubuntu 24.04:

```text
pnpm install --frozen-lockfile
pnpm verificar:expo
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

O checkout não persiste credencial. As actions usam SHA completo, o token possui somente `contents: read`, não existe cache compartilhado e nenhum resultado é publicado como artefato. O pnpm é obtido como binário oficial 11.24.0 e seu checksum é validado antes do uso. A instalação normal usa `strictDepBuilds: true`: qualquer script de dependência ainda não revisado bloqueia. `verifyDepsBeforeRun: error` impede que um comando de qualidade tente instalar ou alterar dependências silenciosamente; somente os passos explícitos de instalação podem fazê-lo.

No mobile, `pnpm build` valida os bundles/exports JavaScript para iOS e Android em Linux. Não compila projeto nativo com Xcode/Gradle, não assina aplicativo e não valida lojas; esses portões pertencem aos PRs mobile/release correspondentes.

### Dependências

O job instala somente o parser pelo lockfile com `--ignore-scripts`, chama diretamente o verificador e solicita ao registro oficial o relatório JSON da árvore completa — runtime e desenvolvimento. A política é default deny:

- qualquer advisory não cadastrado bloqueia, independentemente da severidade;
- a exceção conhecida precisa manter ID, pacote, severidade, versão, classificação e cadeia restrita a pacotes Expo aprovados no mobile;
- `xcode@3.0.1` precisa continuar apontando para `uuid@7.0.3` no lockfile;
- novo ancestral, mudança de ligação ou versão bloqueia;
- a exceção bloqueia após 29 de setembro de 2026;
- desaparecimento do advisory também bloqueia até a exceção obsoleta ser removida.

A última regra evita que uma permissão de risco sobreviva à dependência que a justificava.

### Segredos

O job de segredos:

1. obtém todo o histórico com credencial não persistida;
2. baixa o binário oficial Gitleaks 8.30.0 por HTTPS;
3. valida o SHA-256 antes de extrair;
4. usa configuração protegida que estende as regras padrão, arquivo de fingerprints vazio e `--ignore-gitleaks-allow`;
5. gera em arquivo temporário um PAT sintético não sequencial e exige que o scanner o rejeite;
6. examina o histórico com valores ocultados;
7. não envia relatório ou achado como artefato.

O scanner roda isolado dos comandos do projeto e antes de qualquer necessidade de instalação naquele job.

## Invariantes e riscos

- Não usa `pull_request_target`, runner próprio, environment, OIDC ou segredo.
- Não interpola título, corpo, branch ou outro campo do evento em comando shell.
- Não usa `continue-on-error` em portão.
- Concorrência cancela execução anterior da mesma referência para limitar consumo abusivo.
- A agenda semanal detecta advisory novo sem depender de outro commit.
- Nenhum resultado deste workflow pode ser promovido ou implantado; release futuro reconstrói a partir do commit integrado.
- Um pull request altera o próprio código executado pelo CI. Por isso as configurações remotas abaixo e revisão dos arquivos protegidos são parte do aceite operacional.

## Configuração remota obrigatória

Estas opções não vivem no Git e devem ser aplicadas no GitHub depois que o repositório estiver autenticado e as branches forem enviadas:

1. token padrão do workflow somente leitura;
2. GitHub Actions sem permissão para criar ou aprovar pull requests;
3. permitir somente actions do GitHub, com exigência de SHA completo quando o plano oferecer essa opção;
4. ruleset da `main` exigindo pull request e os checks `Qualidade e build`, `Dependências`, `Segredos no histórico` e, a partir da PR 004, `Ambiente Docker Compose`;
5. revisão de proprietário para `.github/**`, manifestos, lockfile, configuração, scripts e testes dos portões;
6. forks sem token de escrita, sem segredos e com aprovação para primeira execução;
7. Secret Scanning e Push Protection habilitados;
8. Dependency Graph e Dependabot alerts habilitados;
9. retenção curta de logs e nenhum artefato por padrão.

Sem ruleset, um pull request poderia trocar a definição do próprio portão mantendo o mesmo nome do check. `CODEOWNERS` só se torna obrigatório quando a proteção da branch exige essa revisão.

## Testes e evidência de aceite

- parser YAML valida a sintaxe e a topologia do workflow;
- teste exige SHA de 40 caracteres em toda action e checksum exato para os binários;
- teste exige checkout sem credencial, token somente leitura, runner hospedado e timeout;
- teste proíbe eventos privilegiados, segredo e interpolação de evento em shell;
- testes negativos cobrem advisory novo, severidade alta, ancestral não aprovado, mudança da ligação `xcode`/`uuid`, expiração, exceção obsoleta e relatório inconsistente;
- o Gitleaks precisa detectar seu canário antes de examinar dados reais;
- a matriz de dependências do Expo precisa estar coerente;
- o scanner real de dependências precisa aceitar somente o advisory conhecido;
- lint, typecheck, testes e builds completos devem passar localmente antes do merge;
- a primeira execução real no GitHub deve ser anexada ao PR como evidência após autenticação.

## Migration, compatibilidade e rollback

Não existe migration nem estado de produção. O rollback remove o workflow, os scripts, a configuração e os testes deste PR e também remove, de forma coordenada, os required checks correspondentes do ruleset para não bloquear todos os merges. Isso desliga proteção e, portanto, exige decisão de segurança; não afeta dados ou binários já publicados.

## Escolha do storage

O MinIO comunitário da PR 004 é legado e permanece restrito ao desenvolvimento. Para o staging mínimo foi escolhido o [Garage](https://garagehq.deuxfleurs.fr/), storage S3 compatível voltado a implantação autogerenciada pequena/média. O projeto publica documentação, releases e política de reporte de segurança; a imagem oficial é `dxflrs/garage`.

A versão 2.3.0 acrescenta inicialização declarativa de nó único, mas o projeto [adverte expressamente](https://garagehq.deuxfleurs.fr/documentation/quick-start/) que nó único não possui redundância e não deve ser usado em produção. A PR aceita esse limite somente porque:

- o ambiente é staging em uma única VM;
- nenhum dado bruto de produção é permitido;
- perda total do storage não pode causar perda de negócio;
- o objetivo é validar integração, build e operação antes de produção;
- produção continuará exigindo storage externo/redundante aprovado.

Garage mantém metadados em SQLite com `fsync`, blocos com `fsync` e snapshot de metadados a cada seis horas. Segundo a [referência oficial de configuração](https://garagehq.deuxfleurs.fr/documentation/reference-manual/configuration/), SQLite evita limitações de portabilidade/corrupção do LMDB em nó único, embora entregue menos desempenho que um cluster LMDB. Esse compromisso é adequado ao staging mínimo e não congela a solução de produção.

O endpoint S3 não oferece TLS nativo. Nesta topologia ele não sai da rede Docker interna; apenas a API o acessa. Administração e métricas também ficam internas, com tokens lidos de arquivo. O [endpoint oficial de saúde](https://garagehq.deuxfleurs.fr/documentation/reference-manual/admin-api/) e o CLI local validam quórum antes da API subir.

## Licença e distribuição

Garage é AGPL-3.0. Ele é executado como processo separado e a aplicação conversa por S3; nenhum código ou biblioteca Garage é incorporado ao binário da Vyntra. A imagem e o aviso de licença permanecem identificados neste documento. Distribuição futura de um appliance deve preservar as obrigações da imagem e passar por revisão jurídica própria.

## Imutabilidade e atualização

O Compose fixa tag e digest do índice OCI multiarch:

```text
docker.io/dxflrs/garage:v2.3.0@sha256:866bd13ed2038ba7e7190e840482bc27234c4afaf77be8cfa439ae088c1e4690
```

O índice contém manifests Linux `amd64`, `arm64`, `386` e `arm`. A VM de staging usa `amd64`. Não usar `latest`.

Antes de atualizar:

1. revisar notas de versão, migrações e política de segurança;
2. confirmar licença e digest do índice oficial;
3. criar snapshot de metadados e cópia dos dados de staging necessários;
4. validar a nova imagem em projeto/volumes efêmeros;
5. executar smoke S3, reinício e leitura do objeto;
6. atualizar Compose, testes e este registro no mesmo PR.

Uma alteração de major não ocorre automaticamente. A [documentação oficial de upgrade](https://garagehq.deuxfleurs.fr/documentation/operations/upgrading/) é obrigatória antes da troca.

## Riscos residuais aceitos

- Garage, PostgreSQL, Redis e API estão na mesma VM de staging;
- storage em nó único perde disponibilidade e pode perder dados com perda da VM/volume;
- o bucket não substitui backup nem storage de produção;
- o processo Garage roda como root dentro do contêiner scratch para escrever volumes root-owned, porém usa filesystem raiz somente leitura, `cap_drop: ALL`, `no-new-privileges` e nenhuma porta no host;
- o scanner de imagens ainda pertence a evolução posterior do pipeline; versão/digest e smoke não substituem esse portão.

Esses riscos são incompatíveis com produção e aceitáveis apenas para dados sintéticos/sanitizados em staging.

# PR 077 — nós de identidade, cliente e contrato

## Implantação

1. Confirmar `20260901012500_espera_resposta_fluxo` como última migration; esta PR não cria migration.
2. Implantar API e todas as instâncias de `worker_fluxos` com a imagem PR 077.
3. Confirmar `/api/v1/saude/pronto` como `PRONTO`.
4. Habilitar os quatro nós somente depois de workers homogêneos e contratos de entrada estruturada aprovados.

## Aceite

- confirmar contexto explícito sem escolher primeiro vínculo ou preferencial;
- selecionar cliente por UUID sensível exato e limpar contrato anterior;
- selecionar contrato somente sob o cliente atual;
- recusar vínculo revogado, temporário, sem prova ou de outro contato;
- repetir a mesma escolha sem nova escrita/auditoria;
- comprovar versão e auditoria da troca com apenas referências internas;
- comprovar fallback textual do pedido de dados sem fingir capacidade oficial;
- confirmar que passo e log não expõem variável nem UUID escolhido, e que a auditoria contém somente referências UUID internas dos vínculos alterados, sem dado pessoal ou ID externo ERP;
- recusar publicação com parâmetros, referências, tipo ou sensibilidade incompatíveis.

## Recuperação

Não alterar vínculo ou contexto por SQL. Falha de seleção segue a saída configurada ou encaminha ao humano. Corrigir prova/revogação pelo caso de uso autorizado e publicar nova versão para configuração incorreta.

Rollback preserva contexto e auditoria. Antes de voltar ao worker PR 076, interromper novas execuções e comprovar que nenhuma execução não terminal depende dos nós desta PR.

## Resultado em staging

Aceite concluído em 1º de setembro de 2026 sem migration nova, com
`20260901012500_espera_resposta_fluxo` como marca mais recente, API pronta e
duas instâncias do worker PR 077. Quatro execuções sintéticas concluíram 22
passos em 22 pares execução/revisão únicos. O vínculo exato foi selecionado
mesmo havendo outro preferencial; vínculo temporário e vínculo revogado foram
recusados; contrato pertencente a outro cliente não foi aplicado.

O contexto válido avançou de cliente para cliente+contrato com versões 1 e 2;
o cenário cruzado manteve somente o cliente. Houve três auditorias de mutação
com apenas UUIDs internos de vínculo, zero nome de variável ou identificador ERP
externo, e nenhum UUID selecionado em passo. O pedido de dados percorreu
`FALLBACK` e criou exatamente uma mensagem automática com texto seguro. A API
permaneceu `PRONTO`, os dois workers ficaram estáveis e não emitiram falhas.

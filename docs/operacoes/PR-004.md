# PR 004 — Docker Compose de desenvolvimento

## Objetivo e limite

Esta PR entrega apenas o ambiente local aprovado no roadmap:

- API NestJS mínima, ainda sem endpoint de negócio;
- PostgreSQL;
- Redis;
- MinIO compatível com S3;
- volumes persistentes e segredos fora do Git.

Na entrega original, não incluía Prisma, migration, worker, bucket de negócio, Nginx, staging, produção ou integração externa. A PR 007 acrescentou saúde formal e a PR 008 acrescentou Prisma e o job único de migration sem alterar o isolamento desta topologia.

## Topologia local

```text
host
├── 127.0.0.1:3000 → api
├── 127.0.0.1:9000 → MinIO / S3
└── 127.0.0.1:9001 → console MinIO

rede_dados interna
├── api
├── postgres       sem porta no host
└── redis          sem porta no host

rede_publicada_local
├── api            publicada apenas em 127.0.0.1
└── minio          publicado apenas em 127.0.0.1
```

Uma bridge não interna separada é necessária para que Engines Docker atuais apliquem a publicação de portas. Ela não publica nada por si só: as três portas continuam explicitamente presas a `127.0.0.1`. PostgreSQL e Redis ficam somente em `rede_dados`; a API participa das duas redes e acessa o MinIO pela bridge local. O serviço `preparar_volume_minio` somente ajusta a permissão do volume e termina. Ele não recebe rede nem segredo. O servidor MinIO roda com UID diferente de zero, root filesystem somente leitura e todas as capabilities removidas.

## Pré-requisitos

- Node.js compatível com a versão da raiz;
- pnpm 11.24.0;
- Docker Desktop/Engine com Docker Compose recente e suporte a `docker compose up --wait`;
- portas locais 3000, 9000 e 9001 livres, ou outras portas não privilegiadas definidas no shell/`.env` local.

`.env.example` contém somente portas. Credenciais não passam por esse arquivo.

## Primeiro uso

```text
pnpm ambiente:preparar
pnpm ambiente:validar
pnpm ambiente:subir
```

`ambiente:preparar` cria, sem sobrescrever material existente:

```text
.segredos/desenvolvimento/senha-postgresql
.segredos/desenvolvimento/usuario-minio
.segredos/desenvolvimento/senha-minio
.segredos/desenvolvimento/redis.acl
```

Em sistemas POSIX, o diretório usa `0700`; a senha do PostgreSQL usa `0640`, pois API e migration executam com UID sem root e grupo primário `0`. Os três arquivos consumidos pelos outros processos sem root usam `0644` dentro desse diretório não atravessável. O Docker Compose local monta arquivos secretos por bind e não remapeia UID/GID/modo como o Swarm. Assim, outros usuários do host continuam sem acesso, enquanto cada contêiner lê somente o arquivo individual montado. O comando nunca mostra os valores. Modo diferente do esperado, conteúdo fora do formato ou symlink bloqueia a validação. No primeiro uso, os quatro arquivos são criados juntos; se apenas parte do conjunto existir, a preparação falha sem regenerar nada.

Segredos e volumes formam um par operacional. Em especial, o PostgreSQL aplica a senha somente ao inicializar um volume vazio. Se um segredo for perdido com o volume preservado, restaure o segredo ou faça uma rotação deliberada dentro do serviço; não gere outro valor por cima. Para dados estritamente sintéticos, a alternativa é o reset manual e explicitamente destrutivo descrito abaixo.

`ambiente:subir` volta somente quando PostgreSQL, Redis, MinIO e API estão saudáveis e o job `migrar` terminou com sucesso. Para consultar o estado ou parar preservando dados:

```text
pnpm ambiente:estado
pnpm ambiente:parar
```

O wrapper usa sempre o `compose.yaml` deste repositório, fixa o nome do projeto e recusa contexto Docker remoto. No Docker Desktop para macOS, o contexto local ativo (`desktop-linux`) é aceito após validar que seu endpoint é um socket local.

Em hosts Linux usados para testes persistentes, configure `vm.overcommit_memory=1` conforme a [orientação operacional do Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/admin/). Aplique a configuração em arquivo próprio sob `/etc/sysctl.d/` e confirme com `sysctl vm.overcommit_memory`. No Docker Desktop, essa configuração pertence à VM administrada pelo próprio Desktop, não ao macOS hospedeiro.

## Portas opcionais

Somente as portas publicadas em loopback podem ser alteradas:

```text
PORTA_API=3100
PORTA_MINIO=9100
PORTA_CONSOLE_MINIO=9101
```

PostgreSQL e Redis permanecem internos. Após confirmar que o contexto ativo aponta para `unix://` ou `npipe://`, o diagnóstico pontual usa `docker compose --file compose.yaml --project-name vyntra-desenvolvimento exec ...`, não publicação ampla de porta. Nunca copie esse comando para um contexto remoto.

## Persistência e limpeza

Os volumes são:

```text
dados_postgresql → /var/lib/postgresql
dados_redis      → /data
dados_minio      → /data
```

PostgreSQL é a futura fonte da verdade. Redis usa AOF neste ambiente para tornar reinícios previsíveis, mas continua sendo arquiteturalmente descartável. MinIO guarda somente dados sintéticos locais.

`pnpm ambiente:parar` executa `down` no arquivo/projeto fixos sem remover volumes. Para apagar todo o estado local, primeiro confira o contexto, seu endpoint e o projeto exato:

```text
docker context show
docker context inspect "$(docker context show)" --format '{{.Endpoints.docker.Host}}'
docker --context "$(docker context show)" compose ls
```

Prossiga somente se o endpoint começar por `unix://` ou `npipe://` e a lista contiver `vyntra-desenvolvimento`. Então, ciente de que não há recuperação automática, execute manualmente:

```text
docker --context "$(docker context show)" compose --file compose.yaml --project-name vyntra-desenvolvimento down --volumes --remove-orphans
```

Não automatize esse reset em scripts de uso diário e nunca use alvo amplo, diretório raiz ou variável não resolvida.

## Segurança local

- imagens externas têm versão exata e digest de índice multiarch;
- nenhum serviço usa `latest`, `container_name`, rede do host, modo privilegiado ou socket Docker;
- API e MinIO não rodam como root;
- arquivos `0644` permanecem protegidos pelo diretório local `0700` e chegam somente ao serviço que os declara;
- PostgreSQL e Redis não são publicados no host;
- S3 e console MinIO ficam somente em `127.0.0.1`;
- MinIO não cria bucket nem política pública;
- logs Docker têm rotação local;
- `.dockerignore` exclui Git, segredos, ambientes, dependências e aplicações fora da API;
- a imagem final da API contém somente o runtime portátil gerado por `pnpm deploy --prod`.

## Exceção restrita do MinIO

Em 2026, o projeto comunitário MinIO foi arquivado e os binários comunitários passaram a ser legados. Os avisos oficiais [GHSA-hv4r-mvr4-25vw](https://github.com/minio/minio/security/advisories/GHSA-hv4r-mvr4-25vw) e [GHSA-xh8f-g2qw-gcm7](https://github.com/minio/minio/security/advisories/GHSA-xh8f-g2qw-gcm7) afetam a linha pública final e apontam correções mantidas no AIStor.

O Compose mantém a última imagem pública multiarch somente porque a decisão aprovada exige MinIO no desenvolvimento. A exposição fica limitada a loopback e à bridge local dedicada, com credenciais aleatórias, usuário sem root e proibição de dados reais. Essa mitigação reduz a superfície, mas não transforma a imagem em dependência adequada para staging ou produção.

Antes da PR 005, é obrigatório escolher uma destas rotas para o storage de staging, mediante revisão técnica, jurídica e de segurança:

1. storage S3 mantido e aprovado para o ambiente;
2. AIStor mantido, com licença própria e segredo fora do Git.

Uma decisão arquitetural por outro emulador S3 pode substituir o MinIO apenas no desenvolvimento; ela não satisfaz o portão de storage mantido de staging.

Não trocar silenciosamente a imagem, aceitar licença em nome da empresa nem promover o volume local.

## CI e aceite

O job `Ambiente Docker Compose`:

1. gera segredos sintéticos;
2. valida o Compose sem imprimir a configuração interpolada;
3. constrói e sobe a pilha com nome de projeto exclusivo;
4. confirma o `404` HTTP da API mínima;
5. grava marcadores em PostgreSQL, Redis e MinIO;
6. reinicia os três serviços e comprova os marcadores;
7. remove contêineres e volumes efêmeros mesmo se o smoke test falhar.

A conexão de verificação do PostgreSQL ocorre por TCP com o arquivo secreto; Redis também autentica pelo ACL. No MinIO, o cliente `mc` incluído na imagem autentica pelos dois arquivos secretos, cria um bucket estritamente efêmero de verificação e comprova o objeto após o reinício. Isso testa protocolo S3 e volume sem antecipar bucket ou política de negócio. Os testes estáticos bloqueiam porta fora de loopback, imagem externa sem digest, segredo literal, privilégio amplo, bind mount, ausência de healthcheck e alteração indevida do escopo.

## Reversão

1. `pnpm ambiente:parar` para os serviços e preserva dados;
2. reverta os arquivos da PR;
3. mantenha os volumes até decidir explicitamente se os dados sintéticos podem ser descartados.

Não existe migration nem alteração de schema nesta PR. Reverter o código não exige apagar volume.

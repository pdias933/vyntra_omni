# PR 005 — Staging isolado mínimo

## Objetivo e limite

Esta PR cria o primeiro ambiente de staging executável e isolado:

- projeto Docker Compose próprio;
- PostgreSQL próprio;
- Redis próprio;
- storage S3 próprio e mantido;
- redes, volumes e segredos próprios;
- API mínima construída do mesmo código promovível;
- smoke test de cada dependência;
- bloqueio operacional contra dados brutos de produção.

Não inclui Nginx/HTTPS público, domínio, Cloudflare, Meta, MK Solutions, migrations, worker, backup externo, deploy automático ou produção. A API continua sem endpoint de negócio e responde `404` em `/`; `/saude/vivo` e `/saude/pronto` pertencem à PR 007.

## Topologia

```text
VM de staging
│
├── 127.0.0.1:3100 → api
│
├── rede_dados_staging (interna)
│   ├── api
│   ├── postgres:5432
│   └── redis:6379
│
├── rede_storage_staging (interna)
│   ├── api
│   └── storage:3900/3901/3903
│
└── rede_publicada_staging
    └── api → somente loopback
```

PostgreSQL, Redis, S3, RPC e administração do storage não publicam porta no host. O acesso à API por operador ocorre por loopback local ou túnel SSH; não há HTTP público nesta PR.

O nome do projeto é fixo em `vyntra-staging`. Volumes não são externos e recebem o prefixo desse projeto, portanto não podem apontar silenciosamente para volumes do desenvolvimento ou produção.

## Guardas de isolamento

O wrapper `scripts/ambiente-staging.mjs`:

- fixa `compose.staging.yaml` e o projeto `vyntra-staging`;
- remove overrides `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME`, `DOCKER_HOST` e equivalentes;
- recusa contexto Docker remoto;
- exige o conjunto indivisível `.segredos/staging/`;
- recusa arquivo, diretório ou symlink com modo inesperado;
- exige o marcador `VYNTRA_AMBIENTE=staging` e `DADOS_PERMITIDOS=sinteticos_ou_sanitizados`;
- exige confirmação literal para subir ou parar;
- não contém comando de importação, restore, cópia de banco ou reset de volume;
- preserva volumes ao parar.

A confirmação obrigatória é:

```text
VYNTRA_CONFIRMAR_STAGING=STAGING_ISOLADO_SEM_DADOS_DE_PRODUCAO
```

Ela reduz erro operacional, mas não torna uma cópia de produção aceitável. Fixtures devem ser criadas sinteticamente ou passar por processo de sanitização aprovado fora desta PR.

## Segredos

No primeiro preparo são criados juntos, sem sobrescrever:

```text
.segredos/staging/marcador-ambiente
.segredos/staging/senha-postgresql
.segredos/staging/url-postgresql
.segredos/staging/redis.acl
.segredos/staging/url-redis
.segredos/staging/garage-rpc
.segredos/staging/garage-admin
.segredos/staging/garage-metricas
```

Após o storage iniciar, Garage gera uma chave própria e o wrapper grava uma única vez:

```text
.segredos/staging/chave-storage-id
.segredos/staging/chave-storage-secreta
```

O diretório usa `0700`. Segredos consumidos apenas por processos root usam `0600`; `url-postgresql`, `url-redis`, `chave-storage-id` e `chave-storage-secreta` usam `0640`, pois a API executa como UID sem root e grupo primário `0`; `redis.acl` usa `0644`, pois o Redis sem root precisa ler o bind individual do Compose. O Compose local monta segredos por bind e não remapeia proprietário/modo: esses modos são necessários para leitura sem tornar o processo root. O diretório não atravessável continua bloqueando leitura direta no host e cada arquivo é montado somente no serviço que o declara.

Senha, URL autenticada e chave não aparecem em Git, Compose, imagem, log, saída do preparo, variável de ambiente com valor ou argumento de processo. A criação da chave usa a API administrativa local do Garage por entrada padrão; apenas o resultado em memória é persistido nos arquivos protegidos.

Se apenas parte do conjunto existir, o wrapper para. Não regenere segredo sobre volume existente: PostgreSQL, Redis e Garage continuariam esperando o valor anterior. Restaure o arquivo ou faça rotação deliberada no serviço.

## Storage S3

Garage 2.3.0 executa em nó único com:

- bucket privado `vyntra-staging-midias`;
- chave `vyntra-staging-aplicacao`;
- leitura e escrita somente nesse bucket;
- sem permissão de proprietário;
- sem website ou política pública;
- SQLite para metadados;
- `metadata_fsync` e `data_fsync` ativos;
- snapshot de metadados a cada seis horas;
- volumes distintos para blocos, metadados e snapshots.

O wrapper verifica divergência entre chave persistida localmente e chave cadastrada no Garage. Se o servidor tiver a chave mas o arquivo secreto tiver sido perdido, a subida falha com `CHAVE_STORAGE_EXISTE_SEM_SEGREDO_LOCAL`; não cria outra chave nem enfraquece acesso silenciosamente.

Nó único não possui redundância. O dado de staging é descartável e não pode ser a única cópia de evidência necessária. Produção exige storage externo/redundante aprovado.

## Pré-requisitos da VM

- Linux x86-64 ou ARM64 suportado pelas imagens;
- Docker Engine e plugin Compose com `up --wait`;
- Node.js 24 compatível com a raiz para executar o wrapper;
- `vm.overcommit_memory=1` persistido para Redis;
- acesso SSH por chave e firewall sem portas de dados públicas;
- diretório de implantação exclusivo e acesso administrativo restrito.

## Primeiro deploy

No checkout correto da PR 005:

```text
pnpm staging:preparar
pnpm staging:validar
VYNTRA_CONFIRMAR_STAGING=STAGING_ISOLADO_SEM_DADOS_DE_PRODUCAO pnpm staging:subir
pnpm staging:estado
```

`staging:subir` executa na ordem:

1. valida contexto Docker e segredos-base;
2. sobe PostgreSQL, Redis e Garage e aguarda saúde;
3. cria/reconcilia bucket e chave de menor privilégio;
4. constrói e sobe a API;
5. valida Garage, PostgreSQL, Redis e `404` da API.

O smoke pode ser repetido sem mutação de negócio:

```text
pnpm staging:smoke
```

## Estado e acesso

```text
pnpm staging:estado
ssh -L 3100:127.0.0.1:3100 usuario@vm-staging
```

Com o túnel ativo, `http://127.0.0.1:3100/` deve responder `404` nesta etapa. Não publique `3100` em `0.0.0.0` para contornar ausência de proxy/TLS.

## Parada e reinício

Parar preservando volumes:

```text
VYNTRA_CONFIRMAR_STAGING=STAGING_ISOLADO_SEM_DADOS_DE_PRODUCAO pnpm staging:parar
```

Subir novamente usa os mesmos segredos, volumes, bucket e chave. `restart: unless-stopped` permite recuperação após reinício da VM, desde que Docker esteja habilitado.

O wrapper não oferece remoção de volumes. Um reset total é destrutivo e só pode ser feito manualmente após confirmar projeto, diretório, dados descartáveis e ausência de qualquer volume de outro ambiente. Não usar glob, nome parcial nem variável não resolvida.

## Verificações de aceite

- `docker compose ls` mostra `vyntra-staging` separado de `vyntra-desenvolvimento`;
- quatro serviços ficam saudáveis;
- apenas `127.0.0.1:3100` aparece publicado;
- PostgreSQL aceita consulta autenticada no banco `vyntra_staging`;
- Redis exige o usuário `vyntra_staging` e responde `PONG`;
- Garage informa `healthy`, bucket privado e chave sem `owner`;
- reinício dos contêineres preserva banco, cache e storage;
- varredura de segredos não encontra material versionado;
- testes estáticos recusam credencial de produção, storage legado, porta de dados e volume externo.

### Evidência executada

Aceite realizado em 30 de agosto de 2026 na VM de testes aprovada:

- `vyntra-desenvolvimento` e `vyntra-staging` permaneceram simultaneamente saudáveis e com arquivos Compose distintos;
- staging apresentou exatamente `api`, `postgres`, `redis` e `storage` saudáveis;
- somente `127.0.0.1:3100` foi publicado pelo staging; portas 3900/3901/3903, 5432 e 6379 não apareceram no host;
- foram criados cinco volumes e três redes com prefixo exclusivo `vyntra-staging`;
- os dez arquivos secretos apresentaram os modos esperados e nenhum valor foi impresso;
- a verificação assinada AWS SigV4 gravou e leu um objeto no bucket privado;
- marcadores sintéticos de PostgreSQL, Redis e S3 permaneceram disponíveis após reiniciar os três contêineres;
- o smoke completo passou novamente depois do reinício.

O teste não importou arquivo, banco, fixture ou credencial de produção.

## Reversão

1. parar o projeto de staging preservando volumes;
2. retornar ao commit anterior da aplicação;
3. manter `.segredos/staging/` junto aos volumes até decisão explícita;
4. se a imagem Garage for revertida, respeitar compatibilidade de metadados da versão;
5. repetir `staging:smoke` antes de considerar o ambiente disponível.

Não existe migration de aplicação nesta PR. Reverter código não autoriza apagar os volumes.
